## The Brutal Truth

This is incredibly frustrating because it exposes a fundamental blind spot in how we tested. The happy-path tests all passed — `pnpm dev`, click through login, see badge — but the RLS was Swiss cheese when poked via the anon client directly. We shipped 3 serious security holes that would let users forge their trust status, manipulate trip requests, and fake reviews. **The real lesson is that RLS policy testing through your own API layer is not enough; you must actively attack your own RLS rules using the attack surface (anon/authenticated clients) to find column-level forgery, transition violations, and policy gaps.**

The shame here isn't the bugs (Supabase RLS is genuinely subtle) — it's that we didn't build red-team testing into the Phase 02 acceptance criteria from day one. The code review caught them, but a more junior developer shipping without review would have merged these holes directly to main. For a fintech app or healthcare app, this would be a hard stop; for a ride-share MVP it's a learning moment, but it means Phase 04 (trip board + joining) **must** include proactive red-team RLS testing in the acceptance checklist.

On the upside: all findings were fixed before merge, and the fixes are solid (explicit column GRANTs, narrow policies, server-only operations). The architecture is now defensible.

## Technical Details

### RLS Policy Recursion (Phase 02)

The infinite loop happened because:
```
trips_read policy checked: is user creator OR user in requests for this trip
  → which required checking trip_requests_read
    → which required checking creator from trips
      → (loops back)
```

Fix: Two SECURITY DEFINER PL/pgSQL functions with pinned search_path and explicit execute grants:
```sql
CREATE FUNCTION auth_is_trip_owner(trip_id uuid)
RETURNS boolean AS $$
SELECT creator_id = auth.uid() FROM trips WHERE id = trip_id
$$ LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = public;

GRANT EXECUTE ON FUNCTION auth_is_trip_owner(uuid) TO authenticated;
```

Then policies could call `auth_is_trip_owner(trip_id)` without recursion.

### Column-Level Forgery (Phase 02 H1)

Postgres role `authenticated` was created with default column privileges. Schema:
```sql
CREATE TABLE profiles (
  id uuid PRIMARY KEY,
  sv_verified boolean DEFAULT false,  -- should be server-only
  rating_avg numeric(2,1),             -- should be server-only
  zalo_id text UNIQUE,                 -- should be server-only
  name text,                           -- client-writable
  ...
);

GRANT SELECT, INSERT, UPDATE ON profiles TO authenticated;
```

This granted UPDATE on every column. Fix:
```sql
REVOKE UPDATE ON profiles FROM authenticated;
GRANT UPDATE (name, gender, women_pref) ON profiles TO authenticated;
```

Verification: `UPDATE profiles SET sv_verified=true WHERE id=...` returned 0 rows when executed as `authenticated` role (now enforced by policy).

### OTP Rate Limit Bypass (Phase 03 H1)

Original code:
```typescript
// app/api/auth/verify-email/start
const otp = generateOTP();
const hashed = await hash(otp);
// inserts row or updates existing
await upsertOTP(user_id, hashed, { attempts: 0, expires_at: now+15min });
await email.send(...); // could fail
```

Problems:
1. No per-user global rate limit (only attempt cap per row).
2. Each call to `start` reset the row, making the cap meaningless.
3. Email send failure didn't clean up orphaned row.

Fix:
```typescript
const { count } = await db
  .from('sv_otp_sends')
  .select('*', { count: 'exact' })
  .eq('user_id', user.id)
  .gte('created_at', new Date(Date.now() - 15*60*1000))
  .limit(3);

if (count >= 3) return 429; // Rate limit

// only then upsert
await db.from('sv_otp').upsert({...}, { onConflict: 'user_id' });

try {
  await sendEmail(...);
} catch (e) {
  await db.from('sv_otp').delete().eq('user_id', user.id);
  throw e;
}
```

Plus: migrate `sv_otp` to add `created_at` for tracking sends, and add table `sv_otp_sends` for per-user rate limit window.

### Email Validation Gotcha (Phase 03)

First attempt: `const domain = email.split('@')[1]`  
Attack: `x@evil.com@edu.vn` → domain extracted as `evil.com@edu.vn`, fails basic whitelist check but looks wrong.

Fix:
```typescript
const parts = email.split('@');
if (parts.length !== 2) throw new Error('invalid_email');
const domain = parts[1].toLowerCase();
if (!ALLOWED_DOMAINS.includes(domain)) throw new Error('domain_not_allowed');
```

Tested: `x@edu.vn@evil.com` → invalid; `x+alias@edu.vn` → valid (RFC5321 allows `+`).

### Supabase SSR Version Mismatch (Phase 03)

`@supabase/ssr@0.5.2` generated types incompatibility:
- `lib/db/types.ts` defines `Database` from schema introspection.
- Old SSR package's TypeScript plugin expected a different shape.
- Result: all queries typed as `never`, breaking type safety.

Upgrade to `@supabase/ssr@0.12.7` fixed it. The `pnpm-lock.yaml` diff shows a hop from 0.5.2 → 0.12.7 (7 month jump, but stable release).

## What We Tried

1. **RLS recursion:** Started with checking `auth.uid()` directly in trip_requests_read, but that required subquery to trips table anyway. Shifted to extracted SECURITY DEFINER functions (cleaner, stops recursion, audit-friendly).

2. **Column hiding:** First thought was to put all columns in a single table and rely on row-level RLS. Realized RLS is row-level only; column privacy needs explicit column GRANTs or separate tables. Chose explicit GRANTs for trust fields (faster than separate tables, simpler RLS policies).

3. **OTP rate limit:** Tried putting rate limit check in the client (nonsense). Then tried per-row attempt cap (insufficient). Finally added global per-user send window (3 sends/15 min) + atomic attempt increment.

4. **ThemeToggle hydration:** Tried wrapping in Suspense (didn't help). Tried checking `typeof window` (still failed). Fixed by using a static label until mounted: `<ThemeToggle label={mounted ? resolvedTheme : "theme"}`.

5. **Email parsing:** Regex felt overkill; simple split + validation on length was cleaner and sufficient.

## Root Cause Analysis

1. **RLS policy testing through own API layer is insufficient.** We built the schema, wrote policies that made sense, then tested by calling our Next.js API endpoints. The APIs validated input, enforced roles carefully, and called Supabase with service-role keys. Tests passed. But RLS isn't a defense against your own API layer — it's a defense against direct database access. When code review ran the anon client against the raw policies, the holes appeared.

   **Why it happened:** No explicit red-team step in Phase 02 acceptance criteria. The plan said "test hành vi: user B KHÔNG sửa được trip của A" — which we tested, but only via the API. We didn't test: "can user B execute UPDATE as authenticated role against the schema directly?"

2. **Supabase column-level security is not automatic.** Coming from Firebase or other systems, there's an assumption that row-level security handles all privacy. PostgreSQL's GRANT model is more nuanced: RLS filters rows, but column privileges are separate. Once a role CAN select/update a table, it can modify any column unless explicitly GRANTed otherwise. We defaulted to "grant everything, filter by rows" — wrong.

3. **Rate limits on mutable resources are easy to forget.** We had per-attempt caps but no global send limit. Each request to `start` reset state, making the cap a per-record artifact with no window. Rate limiting usually goes hand-in-hand with leaky-bucket or sliding-window logic, not just per-row counts.

4. **Email validation is surprisingly easy to get wrong.** RFC 5321 allows a lot (subdomain parts, `+` addressing, even numeric subdomains). Naively splitting on `@` and taking the last part fails on emails with multiple `@`. A regex or stdlib function is safer than hand-rolled parsing.

5. **Dependency version jumps matter quietly.** The `@supabase/ssr` jump from 0.5.2 → 0.12.7 wasn't a breaking change we had to chase (it was transparent in pnpm-lock.yaml). But the package's TypeScript plugin expectations changed, silently breaking type inference on queries. If we hadn't spotted this during Phase 03 testing, generated types would have been useless in Phase 04.

## Lessons Learned

1. **Red-team RLS from day 1.** For any Postgres schema with RLS, acceptance criteria must include:
   - Happy-path tests via your API (passing is necessary, not sufficient).
   - **Adversarial tests via raw SQL as different roles** (anon, authenticated, service-role, mock JWT claims).
   - Policy matrix: which role can read/insert/update/delete which rows? Test each cell.
   - This is 1–2 hours of work per phase; skip it and you invite security review burnout later.

2. **Column grants are not optional; they're structural.** If you want `sv_verified` to be server-only, it's not enough to not update it in the client code. Write `GRANT UPDATE (name, gender) ON profiles TO authenticated` and test that `UPDATE profiles SET sv_verified=true` returns 0 rows. The first time a code-gen tool or a new engineer reads the schema, they'll get it right by default.

3. **Rate limits need windows and global state, not per-row caps.** If the resource is "send 3 OTPs per user per 15 minutes," model it as a count in a time window, not a cap on attempts that resets per request. Leaky-bucket (counter+timestamp) or sliding-window (list of recent sends) both work; per-row caps don't.

4. **Email validation: regex or stdlib.** The one-liner `email.split('@')[1]` will bite you. Python's `email.utils.parseaddr()`, Node's loose parsing, or a regex like `/^[^@]+@[^@]+\.[^@]+$/` is better than hand-rolled. And always test edge cases: `x@x@y`, `@y`, `x@`, empty string.

5. **Monitor dependency upgrades actively.** Semver says 0.5.2 → 0.12.7 is not a breaking change (both pre-1.0). But plugin expectations, TypeScript symbol exports, and internal type shapes can shift. Run `pnpm outdated` before major releases and test the impact on type inference, not just runtime.

6. **Hydration mismatches are noise until they're not.** ThemeToggle reading `resolvedTheme` before mount is a minor console warning. But in a PWA or SSR-heavy app, it's a signal that you're reading client state on the server. Static fallbacks + useEffect are the pattern.
